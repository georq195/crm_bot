# CRM Telegram-бот для заявок: дизайн

## 1. Цель и контекст

Telegram-бот собирает заявки от клиентов, хранит их в БД и позволяет администраторам вести обработку. Приоритеты проекта: читаемая архитектура, тесты на бизнес-логику, запуск одной командой, понятный README. Надёжность уровня продакшена вторична.

Допущения: один бот обслуживает одну организацию, нагрузка небольшая (десятки заявок в день), интерфейс только на русском, все времена считаются в одном часовом поясе из конфига.

## 2. Стек

| Задача | Выбор |
|---|---|
| Бот | aiogram 3 |
| БД | SQLite, SQLAlchemy 2 (async) + aiosqlite |
| Планировщик | APScheduler |
| Конфиг | `.env` + pydantic-settings |
| Экспорт | `csv` (стандартная библиотека), `openpyxl` |
| Тесты | pytest, pytest-asyncio |
| Запуск | Docker, docker-compose |

Миграций нет. Таблицы создаются при старте через `Base.metadata.create_all()`.

## 3. Роли и права

Роль определяется по `ADMIN_IDS` из `.env`: Telegram ID из списка становятся администраторами, остальные клиентами. Роль пересчитывается при каждом обращении, изменение списка подхватывается после перезапуска контейнера.

| Действие | Клиент | Админ |
|---|---|---|
| Создать заявку | да | да |
| Видеть заявки | только свои | все |
| Редактировать заявку | свою, пока статус «Новая» | нет |
| Менять статус, комментировать | нет | да |
| Фильтр, поиск | нет | да |
| Удалить | нет | да |
| Аналитика, экспорт | нет | да |

## 4. Архитектура

Четыре слоя, зависимости только сверху вниз:

1. `bot/`: роутеры, FSM, клавиатуры, фильтры ролей, тексты. Разбирает ввод и показывает результат. Не содержит SQL и бизнес-правил.
2. `services/`: все правила (переходы статусов, правило редактирования, аналитика, экспорт, уведомления). Не зависит от типов aiogram. Сессию БД и отправителя сообщений получает через аргументы, а не через глобальные объекты.
3. `db/repositories/`: запросы к БД (CRUD, фильтр, поиск, выборки для аналитики).
4. `db/models.py`, `db/base.py`: модели, движок, фабрика сессий, `init_db()`.

Поток запроса (пример «админ меняет статус»): нажатие кнопки приходит в `admin/request_card.py`; middleware уже открыл сессию БД и определил роль; фильтр `IsAdmin` пропускает апдейт; хендлер вызывает `request_service.change_status`; сервис проверяет переход, обновляет заявку, пишет запись в `status_history`, фиксирует транзакцию; затем `notification_service` уведомляет клиента. Ошибка доставки уведомления (бот заблокирован, чат недоступен) не откатывает операцию, а пишется в лог.

Запуск (`main.py`): читает конфиг, вызывает `init_db()`, собирает Dispatcher с middleware и роутерами, стартует APScheduler, запускает polling.

## 6. Модель данных

Все даты хранятся в UTC, пользователю показываются в часовом поясе `TIMEZONE`. В SQLite при каждом подключении выполняется `PRAGMA foreign_keys=ON`, иначе каскадное удаление не работает.

**User**: `id`, `tg_id` (unique), `username`, `full_name`, `role` (client или admin), `created_at`.

**Request**: `id`, `user_id` (FK), `client_name`, `contact`, `description`, `preferred_contact_date` (Date, не в прошлом на момент ввода), `status`, `search_text`, `last_reminded_at` (nullable), `created_at`, `updated_at`, `closed_at` (nullable).

`search_text`: нижний регистр от `client_name` и `contact`, пересчитывается сервисом при создании и редактировании. Нужен потому, что `LIKE` в SQLite нечувствителен к регистру только для ASCII, а для кириллицы нет. Поиск идёт по `search_text` по запросу, приведённому к нижнему регистру в Python.

**Comment**: `id`, `request_id` (FK, `ON DELETE CASCADE`), `author_id` (FK), `text`, `created_at`.

**StatusHistory**: `id`, `request_id` (FK, `ON DELETE CASCADE`), `old_status` (NULL у первой записи), `new_status`, `changed_by` (FK), `changed_at`.

Комментарии внутренние: видны только админам, клиенту не показываются и не рассылаются.

## 7. Статусы и правила

Статус хранится строкой из Enum: `new`, `in_progress`, `done`, `rejected`. Названия для пользователя: Новая, В работе, Завершена, Отклонена.

Допустимые переходы (одна таблица в `request_service`):

| Из | В |
|---|---|
| new | in_progress, rejected |
| in_progress | done, rejected |
| done, rejected | финальные, дальше нельзя |

Переход назад невозможен. Недопустимый переход сервис отклоняет исключением. Кнопки смены статуса в карточке строятся из этой же таблицы.

Правила:
- При создании заявки сразу пишется запись истории `NULL → new`.
- `closed_at` ставится при переходе в `done` или `rejected`.
- Клиент редактирует заявку только в статусе `new`. Проверка выполняется в сервисе в момент сохранения, поэтому гонка с админом, который взял заявку в работу, безопасна.
- Удаление физическое и необратимо: вместе с заявкой удаляются комментарии и история статусов. Клиент об удалении не уведомляется.

## 8. Сценарии бота

Главное меню зависит от роли.
- Клиент: «Новая заявка», «Мои заявки».
- Админ: «Заявки», «Поиск», «Аналитика», «Экспорт», «Новая заявка».

**Создание заявки (FSM):** имя (кнопка с именем из Telegram) → контакт (телефон или @username, лёгкая проверка формата) → описание (не пустое, ограничение длины) → желаемая дата связи (`ДД.ММ.ГГГГ` или кнопки «Сегодня», «Завтра», не в прошлом) → подтверждение («Отправить», «Отмена»). «Отмена» доступна на любом шаге. При ошибке ввода бот объясняет проблему и остаётся на том же шаге.

**Мои заявки (клиент):** список с пагинацией по 5, карточка по нажатию. В статусе `new` в карточке есть «Редактировать»: выбор поля, ввод нового значения с той же проверкой, что при создании. Если заявку успели взять в работу, сервис отклоняет правку и бот сообщает об этом.

**Админ, список:** пагинация по 5, новые сверху, фильтры по статусу (Все, Новые, В работе, Завершённые, Отклонённые). Поиск по имени или контакту, результат показывается тем же списком.

**Админ, карточка:** поля, статус, комментарии. Кнопки «Сменить статус» (только допустимые), «Комментарий», «Удалить» (с подтверждением).

**Устаревшие кнопки:** если заявка уже удалена, бот отвечает «Заявка не найдена» и возвращает в список.

## 9. Уведомления и планировщик

**Уведомления** (`notification_service`):
- Новая заявка: всем админам из `ADMIN_IDS`, кроме автора заявки, с краткой карточкой и кнопкой «Открыть».
- Смена статуса: автору заявки, с названием нового статуса. Тот, кто сменил статус, себя не уведомляет.

**Планировщик** (`scheduler/jobs.py`, APScheduler):
- Напоминание: раз в `REMINDER_INTERVAL_MIN` минут (по умолчанию 60) выбирает заявки в статусе `new` старше `REMINDER_AFTER_HOURS` часов (по умолчанию 4), у которых `last_reminded_at` пуст или старше того же порога, и шлёт админам одно сообщение со списком. После отправки обновляет `last_reminded_at`.
- Ежедневная сводка: в `DAILY_SUMMARY_TIME` (по умолчанию 09:00) по `TIMEZONE`. Содержимое: новые за сутки, сейчас в работе, завершённые за сутки, висящие в «Новая» дольше порога.

## 10. Аналитика

Период выбирается кнопками: сегодня, 7 дней, 30 дней, всё время.
- Количество заявок: по `created_at` в периоде.
- Завершённые: статус `done`, по `closed_at` в периоде.
- Конверсия: доля заявок, дошедших до `in_progress`, от всех; доля дошедших до `done` от дошедших до `in_progress`. Считается по `status_history`.
- Среднее время обработки: `closed_at - created_at` для заявок со статусом `done`.

Ограничение: из-за физического удаления удалённые заявки пропадают и из статистики, поэтому цифры за прошлые периоды могут уменьшиться. Это описывается в README.

## 11. Экспорт

Админ выбирает формат (CSV или XLSX), затем период (по `created_at`) и статус. Бот присылает файл. Если по фильтрам нет заявок, файл не создаётся, бот сообщает об этом.

Колонки: ID, имя, контакт, описание, желаемая дата, статус, создана, закрыта. Даты в `TIMEZONE`.
- CSV: кодировка `utf-8-sig`, чтобы Excel корректно открывал кириллицу.
- XLSX: форматированные заголовки, автоширина колонок.
- Защита от formula injection: значения текстовых ячеек, начинающиеся с `=`, `+`, `-`, `@`, экранируются префиксом `'`.
- Временные файлы лежат в `exports/` и удаляются после отправки.

## 12. Конфигурация

Переменные `.env` (pydantic-settings): `BOT_TOKEN`, `ADMIN_IDS` (через запятую), `DB_PATH` (по умолчанию `data/crm.db`), `TIMEZONE` (по умолчанию `Europe/Moscow`), `REMINDER_INTERVAL_MIN`, `REMINDER_AFTER_HOURS`, `DAILY_SUMMARY_TIME`, `LOG_LEVEL`. При пустом `BOT_TOKEN` или `ADMIN_IDS` бот не стартует и сообщает, чего не хватает.

## 13. Docker

Образ `python:3.12-slim`, запуск `python -m app.main`. `docker-compose.yml`: сервис `bot`, `env_file: .env`, том `./data:/app/data`, `restart: unless-stopped`. Запуск: `docker compose up -d --build`. Часовой пояс контейнера не важен, всё считается по `TIMEZONE`.

## 14. Тесты

pytest + pytest-asyncio, SQLite в памяти, заглушка отправителя сообщений. Покрываются сервисы и репозитории:
- допустимые и недопустимые переходы статусов;
- правило «редактировать только в `new`», включая гонку;
- каскадное удаление комментариев и истории;
- аналитика: количество, конверсия, среднее время на подготовленных данных;
- экспорт: колонки и содержимое CSV и XLSX, экранирование формул;
- регистронезависимый поиск по кириллице;
- выборка для напоминаний и защита от повторов.

Хендлеры Telegram автотестами не покрываются: вся логика проверяется на уровне сервисов.
